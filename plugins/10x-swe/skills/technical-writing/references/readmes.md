# Write a useful README

A README helps a visitor decide whether the project solves their problem and reach
one useful result. Start with the product's purpose, not its package layout.

Start from the [README template](readme-template.md). Keep the shared shape:
a compact identity block, purpose and examples, quick start, setup, usage,
documentation and license. Use a centered title, one-line description, verified
license badge and optional short workflow line for the project family. Keep body
content left-aligned and commands in fenced blocks. Use tables for real choices
or comparisons, not decorative layouts. Avoid badge walls and status dashboards.

Adapt section names and omit unused sections. A library, service or marketplace
needs different examples; visual consistency must not hide required setup or
make an unverified claim. Use only the sections the reader needs:

1. Name and a concrete explanation of what the project helps the reader do.
2. A few recognizable use cases; define unfamiliar concepts through examples.
3. A clear starting choice when multiple plugins, modes or products exist.
4. Requirements and a short installation path.
5. A real first task, with commands or a clearly labeled example request and expected result.
6. Links to deeper guides, reference, architecture, help and licenses.

Place optional advanced paths after the first success. Preserve a useful pipe/API
example when composition is central to the product. Explain input, output and
side effects rather than listing unexplained tool names. Distinguish installation
of instructions from installation of executable tools.

Keep the opening understandable without prior project context. Omit plans,
experiment scores, deployment history and repeated lists of absent features.
Document supported environments and required dependencies precisely. Word count
is a review signal, not a limit that justifies dropping prerequisites.

Before publishing, ask a reader to explain what it does, who it helps and how to
start. Verify commands against the current CLI and test a safe first task when
permitted. If only syntax was checked, record that separately from the README.

Use negative facts to reject false promises during review. In the README, state
the precise positive capability instead: “Default keyword search runs locally”
rather than a list of components that do not run offline. Describe independent
execution and public handoffs; inspect each tool before making storage claims.
